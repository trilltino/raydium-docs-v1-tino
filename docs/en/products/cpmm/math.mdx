## The invariant

CPMM maintains the classic constant-product invariant on its two vaults:

$$
x \cdot y = k
$$

where `x` is the vault0 balance minus the protocol, fund and creator fees still owed in token0, and similarly for `y`. Because the vault balance is what actually arrived, Token-2022 transfer fees are already excluded. These owed fees sit in the vault but are excluded from the curve; see [Fees on the curve](#fees-on-the-curve) below.

Every swap checks `(x + Δx_net) · (y − Δy) ≥ x · y`, where `Δx_net` is the input after **all** input-side fees and `Δy` is the curve's output before any output-side creator fee. The LP share of the trade fee is left out of that check. It stays in the vault and joins `x` for the next swap, so `k` grows over time as LPs accrue fees.

LP shares are priced by the pool's reserves, not by `k`:

$$
\text{LP price in token0} = \frac{x}{\text{lpSupply}}, \qquad \text{LP price in token1} = \frac{y}{\text{lpSupply}}
$$

Burning `ΔLP` LP tokens returns `floor(ΔLP × x / lpSupply)` of token0 and `floor(ΔLP × y / lpSupply)` of token1, where `lpSupply` is `PoolState.lp_supply`, not the LP mint's supply. A deposit pays the same ratio rounded up. Neither changes the price; only swaps do.

## Fee model on the swap path

CPMM applies **two independently-rated fees** on every swap:

- The **trade fee** is always taken on the input side, charged at `AmmConfig.trade_fee_rate`. It is then split into LP, protocol, and fund shares. The LP share stays in the vault and grows `k`. The protocol and fund shares are booked to counters in the input token and excluded from the curve.
- The **creator fee** (active only when `enable_creator_fee == true`) is charged at `AmmConfig.creator_fee_rate`. It is taken on the **input** side or the **output** side depending on `PoolState.creator_fee_on` and the swap direction (see [`products/cpmm/fees`](/docs/en/products/cpmm/fees#which-side-of-the-trade-the-fees-are-taken-from)). It is its own bucket — never a slice of the trade fee.

<Note>
  **The protocol's share of the creator fee does not appear anywhere on this page, and that is deliberate.** It is applied when `CollectCreatorFee` moves accrued fees between two counters that the curve already excludes — not during a swap. Swap math, quotes and `k` are identical with and without it. See [`products/cpmm/fees`](/docs/en/products/cpmm/fees#protocol-share-of-the-creator-fee).
</Note>

Let:

- `FEE_RATE_DENOMINATOR = 1_000_000`
- `trade_fee_rate` — from `AmmConfig`, e.g., `2500` = 0.25% of the swap input
- `creator_fee_rate` — from `AmmConfig`, e.g., `1000` = 0.10% of the input or the output, depending on the side
- `protocol_fee_rate`, `fund_fee_rate` — denominated in units of `1/FEE_RATE_DENOMINATOR` **of the trade fee**, not of volume

When the creator fee is on the input side:

```
total_input_fee = ceil(amount_in * (trade_fee_rate + creator_fee_rate) / FEE_RATE_DENOMINATOR)
creator_fee     = floor(total_input_fee * creator_fee_rate / (trade_fee_rate + creator_fee_rate))
trade_fee       = total_input_fee - creator_fee
amount_in_after_fees = amount_in - total_input_fee
```

When the creator fee is on the output side:

```
trade_fee            = ceil(amount_in * trade_fee_rate / FEE_RATE_DENOMINATOR)
amount_in_after_fees = amount_in - trade_fee
amount_out_curve     = curve_output(amount_in_after_fees, ...)
creator_fee          = ceil(amount_out_curve * creator_fee_rate / FEE_RATE_DENOMINATOR)
amount_out           = amount_out_curve - creator_fee
```

In these formulas, `amount_in` is what reached the vault: the user's amount minus any Token-2022 transfer fee on the input mint.

In both cases the trade fee is split the same way:

```
protocol_fee   = floor(trade_fee * protocol_fee_rate / FEE_RATE_DENOMINATOR)
fund_fee       = floor(trade_fee * fund_fee_rate     / FEE_RATE_DENOMINATOR)
lp_fee         = trade_fee - protocol_fee - fund_fee     // creator_fee is NOT subtracted here
```

The `protocol_fee + fund_fee + creator_fee` amount is held in the vaults but tracked separately on the pool state (`protocol_fees_token*`, `fund_fees_token*`, `creator_fees_token*`). Protocol and fund fees are always booked in the input token. The creator fee is booked in whichever token it was taken from. The program prices every swap from the vault balances **minus** all three counters, so LPs capture only `lp_fee`.

See [`products/cpmm/fees`](/docs/en/products/cpmm/fees) for the collection instructions and the worked numerical examples.

## SwapBaseInput (input-exact)

"The user gives us exactly `amount_in` of the input mint and receives at least `minimum_amount_out` of the output mint."

Ignoring Token-2022 and the creator fee for a moment:

```
Δx_net     = amount_in − trade_fee
amount_out = floor(Δx_net * y / (x + Δx_net))
```

In real numbers this is `y − x·y / (x + Δx_net)`:

$$
\text{amount\_out} = \left\lfloor \frac{y \cdot \Delta x_{\text{net}}}{x + \Delta x_{\text{net}}} \right\rfloor
$$

Don't compute it as `y − floor(x·y / (x + Δx_net))` in integers. That form rounds the output up and can quote one unit more than the program pays.

The program then books the protocol and fund shares of `trade_fee`, and any creator fee, to their counters, which the curve's next `x` and `y` exclude. The LP share does join `x` for the next swap.

### Token-2022 on the input side

If the input mint has a transfer-fee extension, the **mint** deducts its fee on the transfer from user → vault. So the vault actually receives `amount_in − transfer_fee_in`. The CPMM program therefore computes:

```
amount_actually_received = amount_in − transfer_fee_in(amount_in)
trade_fee                = ceil(amount_actually_received * trade_fee_rate / FEE_RATE_DENOMINATOR)
amount_in_after_trade_fee = amount_actually_received − trade_fee
```

and runs the curve against `amount_in_after_trade_fee`. This matters because **the curve price is computed off the net amount that landed in the vault**, not off the user's headline amount.

### Token-2022 on the output side

If the output mint has a transfer fee, the pool sends `amount_out` from its vault to the user. The **mint** withholds its fee on the way out, so the user receives `amount_out − transfer_fee_out(amount_out)`. The program computes `amount_out` from the curve as usual. Your quote must apply the output transfer fee to show what the user receives.

### Slippage check

After computing `amount_out`, the program subtracts the output mint's transfer fee and checks what the user will receive:

```
amount_received = amount_out − transfer_fee_out(amount_out)
require(amount_received > 0)                                   // Anchor RequireGtViolated (2505)
require(amount_received >= minimum_amount_out, ExceededSlippage) // 6005
```

So `minimum_amount_out` is denominated in what the user receives, not in what the vault sends. The SDK's `CurveCalculator` and `computeSwapAmount` don't apply transfer fees. If you derive the minimum from their `outputAmount` on a transfer-fee output mint, the check can fail even when the price hasn't moved.

## SwapBaseOutput (output-exact)

"The user will receive exactly `amount_out` of the output mint and is willing to pay up to `max_amount_in` of the input mint."

The program first works out how much must leave the vault. It adds the output mint's transfer fee to `amount_out`. If the creator fee is on the output side, it then grosses that up for the creator fee: `ceil(amount × D / (D − creator_fee_rate))`. Call the result `Δy`; this is what the curve must deliver.

Inverting the curve for `Δx_net`, with `amount_out` meaning `Δy`:

$$
\Delta x_{\text{net}} = \left\lceil \frac{x \cdot \text{amount\_out}}{y - \text{amount\_out}} \right\rceil
$$

The ceiling is important — it guarantees `k' ≥ k` after integer truncation. Then:

```
// Work backwards from the net in to the gross in.
// fee is applied on the gross, so:
//   net = gross − ceil(gross * rate / D)
//       ≈ gross * (D − rate) / D
// inverting with ceiling in the right places:
gross_needed = ceil(Δx_net * D / (D − trade_fee_rate))
// When the creator fee is on the input side, use (trade_fee_rate + creator_fee_rate)
// in place of trade_fee_rate, then split the difference with the same floor rule as
// SwapBaseInput: creator_fee = floor(total_fee * creator_fee_rate / (trade_fee_rate + creator_fee_rate)).
```

On Token-2022 input, wrap with:

```
gross_needed_before_mint_fee
  = inflate_for_transfer_fee(gross_needed, input_mint)
```

so the user pays enough that after the mint's transfer-fee deduction the pool still receives `gross_needed`.

### Slippage check

```
require(gross_needed_before_mint_fee <= max_amount_in, ExceededSlippage) // 6005
```

Asking for `amount_out = 0` fails with Anchor's `RequireGtViolated` (`2505`). Asking for as much as the output reserve, or more, makes the curve arithmetic fail.

## Worked example

Pool state, ignoring Token-2022:

- `x = 1_000_000_000_000` (1,000,000.000000 of token0, 6 decimals)
- `y = 2_000_000_000_000` (2,000,000.000000 of token1, 6 decimals)
- `AmmConfig`: `trade_fee_rate = 2500`, `protocol_fee_rate = 120_000`, `fund_fee_rate = 40_000`, `creator_fee_rate = 0`

User: `SwapBaseInput` with `amount_in = 1_000_000_000` (1,000.000000 of token0). Creator fee is disabled (`enable_creator_fee = false`).

```
trade_fee                = ceil(1_000_000_000 * 2500 / 1_000_000)       = 2_500_000
  protocol_fee           = floor(2_500_000 * 120_000 / 1_000_000)       = 300_000
  fund_fee               = floor(2_500_000 *  40_000 / 1_000_000)       = 100_000
  lp_fee                 = 2_500_000 − 300_000 − 100_000                 = 2_100_000
creator_fee              = 0                                              // disabled

amount_in_after_trade_fee = 1_000_000_000 − 2_500_000                    = 997_500_000

amount_out = floor(Δx_net * y / (x + Δx_net))
           = floor(997_500_000 * 2_000_000_000_000
                   / (1_000_000_000_000 + 997_500_000))
           = 1_993_011_970

// The swap's own check leaves the whole trade fee out of x:
(x + Δx_net) * (y − amount_out) ≈ 2.000_000_000_000_56E24  ≥  k = 2.0E24   ✓

new_vault0_raw   = x + amount_in                                        = 1_001_000_000_000
new_vault1       = y − amount_out                                       = 1_998_006_988_030

// Of the 1_000_000_000 received in vault0, 400_000 is "accrued fee"
// (protocol + fund) that the curve excludes from now on:
curve_x          = new_vault0_raw − (protocol_fees_token0 + fund_fees_token0)
                 = 1_001_000_000_000 − 400_000
                 = 1_000_999_600_000

// The LP fee (2_100_000) is part of curve_x, so the next swap sees a larger k:
k_next = curve_x * new_vault1 ≈ 2.000_004_196E24
```

If the same pool had `enable_creator_fee = true` with `creator_fee_rate = 1000` (0.10%) on the input side, the program would charge `total_input_fee = ceil(1_000_000_000 * 3500 / 1_000_000) = 3_500_000`, then split it as `creator_fee = floor(3_500_000 * 1000 / 3500) = 1_000_000` and `trade_fee = 2_500_000`. The protocol/fund/LP arithmetic on `trade_fee` is unchanged from the example above. The creator fee is its own bucket, accrued to `creator_fees_token0` and excluded from `curve_x` along with the protocol and fund buckets. `Δx_net` becomes `996_500_000`.

If the input mint has a 1% Token-2022 transfer fee and its maximum fee doesn't cap it, the vault receives `990_000_000` tokens instead of `1_000_000_000`, and every subsequent calculation uses that net amount.

## Observation update rule

Every swap calls the observation update after its transfers. It passes the prices from **before** the swap, computed from the fee-excluded reserves, so each update records the price that held since the previous update:

```
// x, y = fee-excluded reserves before this swap
price0 = y * 2^32 / x                     // token0 priced in token1, Q32.32
price1 = x * 2^32 / y                     // token1 priced in token0, Q32.32

if !initialized:                          // first swap after pool creation
    observations[0].block_timestamp = now // cumulatives stay 0
    last_update_timestamp = now
    return

newest     = observations[observation_index]
since_obs  = now − newest.block_timestamp
since_upd  = now − last_update_timestamp
if since_obs == 0 or since_upd == 0: return

// cumulative_0 / cumulative_1 = cumulative_token_0_price_x32 / cumulative_token_1_price_x32
delta0 = price0 * since_upd
delta1 = price1 * since_upd
if since_obs < 15:                        // OBSERVATION_UPDATE_DURATION_DEFAULT
    newest.cumulative_0 = newest.cumulative_0 wrapping_add delta0
    newest.cumulative_1 = newest.cumulative_1 wrapping_add delta1
else:
    next = (observation_index + 1) % 100
    observations[next] = { block_timestamp: now,
                           cumulative_0: newest.cumulative_0 wrapping_add delta0,
                           cumulative_1: newest.cumulative_1 wrapping_add delta1 }
    observation_index = next
last_update_timestamp = now
```

Deposits, withdrawals and fee collections don't touch the observation account.

Three properties:

- **Cumulative price, not spot price.** A single observation is not a price. To get a TWAP from time `t0` to `t1`, read the observations closest to each end and compute `(cumulative(t1) − cumulative(t0)) / (t1 − t0) / 2^32`, subtracting modulo 2^128.
- **Entries are at least 15 seconds apart.** Swaps within 15 seconds of the newest entry add to that entry instead of starting a new one. Its cumulative can therefore run up to 15 seconds ahead of its `block_timestamp`. For the newest entry, use `last_update_timestamp` as its time.
- **Time before the first swap is not recorded.** The first update only sets the starting timestamp, so accumulation covers the time from the first swap onward.

CLMM's oracle stores a cumulative tick instead, so its TWAP math is different; don't reuse it for CPMM.

## Fees on the curve

This is the subtle part and worth calling out. The curve arithmetic works against the **net** vault balances — i.e., raw SPL balance minus accrued protocol, fund, and creator fees (all three are independent buckets — see [`products/cpmm/fees`](/docs/en/products/cpmm/fees)). A concrete picture:

```
raw_vault_balance   = what an RPC getTokenAccountBalance returns
accrued_fees        = protocol_fees_token{0,1} + fund_fees_token{0,1} + creator_fees_token{0,1}
curve_balance       = raw_vault_balance − accrued_fees
invariant           = curve_balance0 * curve_balance1
```

Consequences for integrators:

- **Do not quote from raw balances.** Subtract the accrued-fee fields first, or simulate `SwapBaseInput` and decode the `SwapEvent` it emits. The instruction itself returns no value.
- **`CollectProtocolFee` moves tokens out of the vault.** It lowers `raw_vault_balance` and the protocol counter by the same amount, so `curve_balance` and the pool's price do not move.

## Precision and overflow

- All curve arithmetic uses `u128` intermediates to prevent overflow on `x * y`.
- Swap outputs, the protocol, fund and creator-share splits, the creator-fee split of a combined input fee, and withdrawal amounts round down. The combined input fee, output-side creator fees, `SwapBaseOutput`'s `Δx_net` and gross input, and the amounts a deposit pays round up. These directions keep the pool from paying out more than the curve allows.
- A deposit or withdrawal where either side rounds to zero fails with `ZeroTradingTokens` (`6006`). A swap whose output, after the output transfer fee, rounds to zero fails with Anchor's `RequireGtViolated` (`2505`), not `ZeroTradingTokens`. See [`reference/error-codes`](/docs/en/reference/error-codes).
