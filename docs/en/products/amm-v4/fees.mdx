## The one published tier

AMM v4 stores fees directly on each pool's `AmmInfo.fees` struct. Its program-wide `AmmConfig` account holds the fee owners and the pool-creation fee, not trading fees, so there are no CPMM- or CLMM-style fee tiers. `Initialize2` takes no fee arguments, so every new pool starts with the published defaults below. The admin can change a pool's fees afterwards with `SetParams`.

| On-chain field | Default | Meaning |
|----------------|---------|---------|
| `swap_fee_numerator / swap_fee_denominator` | `25 / 10_000` | **Gross trade fee on AMM-path swaps: 0.25% of input volume.** |
| `trade_fee_numerator / trade_fee_denominator` | `25 / 10_000` | Vestigial after the OpenBook removal (historically used for limit-order pricing). Same `0.25%` as `swap_fee` by default. |
| `pnl_numerator / pnl_denominator` | `12 / 100` | **Protocol's settlement fraction: 12% of the growth calculated by `calc_take_pnl`.** The commonly quoted `0.03%` of volume is an economic fee equivalent, not an exact per-swap deduction. |
| `min_separate_numerator / min_separate_denominator` | `5 / 10_000` | Only validated (numerator below denominator) since the OpenBook removal. It formerly widened the order grid's bid/ask spread, together with `trade_fee`. |

For the default settings, `pnl_numerator / pnl_denominator` is a fraction of the pool growth calculated at settlement, not of an individual swap fee or trade volume. LPs retain the remaining growth. There is no separate "LP share" numerator.

Always read `AmmInfo.fees` before quoting because the admin can change these values.

There is **no fund-fee** and **no creator-fee** line: these are CPMM/CLMM inventions that did not exist in AMM v4's original fee model.

## How the split is realised

A swap doesn't split the fee. It charges the gross fee off the input amount, and the whole input, fee included, enters the vault:

```
gross_fee = ceil(amount_in * swap_fee_numerator / swap_fee_denominator)   // 0.25% of amount_in
```

The fee raises `k`. The split happens later, when `Deposit`, `Withdraw` or `WithdrawPnl` runs `calc_take_pnl` (`Withdraw` skips it while the pool is `WithdrawOnly`). That step measures how far the reserves have grown since the baseline stored on `TargetOrders`. With the default parameters, it books 12% of the growth into `need_take_pnl_coin` **and** `need_take_pnl_pc`, in proportion to the reserves, and leaves the other 88% in the pool for LPs. If either amount rounds to zero, it books nothing. The formula is in [`products/amm-v4/math`](/docs/en/products/amm-v4/math#settlement-step-pnl).

- Between realisations the protocol's share is still in the curve's reserves, so `need_take_pnl_*` lags the fees swaps have earned.
- Once booked, `need_take_pnl_*` sits in the vault but is subtracted from the reserves the curve uses, so the later sweep doesn't move the price.

## `total_pnl_*` counters (historical)

<Note>
  **Frozen.** The 2026-07 upgrade stopped updating `state_data.total_pnl_{coin,pc}`. They keep their last values. The protocol-fee mechanism is unaffected.
</Note>

Before the removal, `calc_take_pnl` also added the full growth amounts, before applying `pnl_numerator / pnl_denominator` (12% by default), to `total_pnl_pc` and `total_pnl_coin` each time it realised PnL. They were lifetime counters of realised `k` growth. Nothing else wrote them, so they never recorded OpenBook fills as a separate stream. Grid fills changed the reserves like any other trade, so any gain from them showed up in the same growth measure.

Today the only fee is the 0.25% swap fee.

## Collection

`WithdrawPnl` sweeps the protocol fee. The signer must be the program admin (`amm_owner`) or the `pnl_owner` stored on the program-wide `AmmConfig`. The caller supplies the two destination token accounts; the program checks only that their mints match the pool's. It works in any status except `Uninitialized`. It:

1. Realises PnL first: runs `calc_take_pnl`, which adds the protocol's share of the growth since the last baseline to `need_take_pnl_*`.
2. Transfers the full `need_take_pnl_coin` / `need_take_pnl_pc` from the pool vaults to the destination accounts. If either exceeds its vault balance, the call fails with `TakePnlError`.
3. Zeroes the counters and resets the `TargetOrders` baseline.

When step 1 books new PnL, it takes those tokens out of the curve's reserves, so **`k` shrinks**. The price doesn't move, because both sides shrink in proportion. Paying out PnL booked earlier doesn't change `k`, because the curve already excluded it. The `WithdrawPnl` account layout changed in the 2026-07 upgrade (see [instructions](/docs/en/products/amm-v4/instructions#withdrawpnl)).

## LP fee redemption

There is no dedicated "collect LP fees" instruction. LP fees stay in the vaults and raise `k`; LPs collect them by burning LP tokens via `Withdraw`. Swap fees add to the reserves behind each LP token. Booking protocol PnL takes a smaller amount back out. With the default parameters, that amount is 12% of the growth. Neither value tells you an LP token's market value, which also moves with the prices of the two tokens.

## Visualization: where 1,000 USDC of volume goes

On a USDC-heavy swap of \$1,000 against a default-parameter pool:

```
Gross trade fee (0.25%):   $2.50   → stays in the pool at swap time, raises k
  At the next PnL realisation:
  LP economic equivalent:  ≈$2.20   → stays in the pool
  PnL economic equivalent: ≈$0.30   → booked from calculated growth in both tokens
Enters the curve:         $997.50   → the user receives the curve's output for this amount
```

Compare to CPMM `AmmConfig[0]` (0.25% tier, no creator fee): LP gets \$2.10, protocol \$0.30, fund \$0.10. CPMM introduces the fund line by carving it out of what would have been LP's share in AMM v4's equivalent tier.

## Integrator notes

- **Quoting.** Fetch `AmmInfo` via the SDK or `api-v3.raydium.io/pools/info/ids`. Reserves are now vault-only, so you can quote against the vault balances directly — just remember to subtract `need_take_pnl_*` (accrued PnL is held in the vault but excluded from the curve).
- **SDK quotation limitation.** In SDK V2 `0.2.85-alpha`, `liquidity.computeAmountOut()` and `liquidity.computeAmountIn()` use the fixed `25 / 10_000` swap fee. The program reads each pool's `AmmInfo.fees`. If an admin has changed a pool's fee, calculate the quote from the on-chain fee values instead of using these helpers. This is separate from the exact-output rounding issue described in [Code demos](/docs/en/products/amm-v4/code-demos#pitfalls).
- **Read fees from chain.** The admin can change any pool's fees with `SetParams`. A 2026-11-20 Triton mainnet sample found default values in all 3,559 AMM v4 pools returned among the five highest-TVL API pages. The lowest-TVL pool in the sample held about $7,830. Still read `AmmInfo.fees` rather than assuming that a pool uses the defaults.
- **No rewards.** AMM v4 does not support on-pool reward emissions. Ecosystem farms are the staking-layer equivalent: Farm v6 is current, and Farm v3 / v5 are wind-down only — see [`products/farm-staking`](/docs/en/products/farm-staking).
