**In short.** The 16 November demo update prompted this review. The demo repo now creates CPMM pools with an optional creator fee and creates customizable CLMM pools through a new V2 method. The docs still showed the old SDK calls, and several overview pages described the CPMM creator fee as a slice of the trade fee. The published `0.2.85-alpha` SDK and the program source, not the demo, confirmed each documentation change. For example, the demo now calls `createCustomizablePoolV2`, but the SDK source shows that this builder creates an additional seed-indexed pool. The CLMM example therefore keeps `createCustomizablePool` as the default. This pass updates the examples, corrects the fee model on every page that summarized it, warns about SDK quote and fee-payer gaps, and moves the documentation's SDK pin from `0.2.64-alpha` to `0.2.85-alpha`.

## Upstream demo changes

### CPMM: `src/cpmm/createCpmmPool.ts`

The file's exported function is named `createPool`.

```diff
 import {
   CREATE_CPMM_POOL_PROGRAM,
   CREATE_CPMM_POOL_FEE_ACC,
   DEVNET_PROGRAM_ID,
   getCpmmPdaAmmConfigId,
   printSimulate,
+  FeeOn,
 } from '@raydium-io/raydium-sdk-v2'
```

```diff
     startTime: new BN(0),
     feeConfig: feeConfigs[0],
+    creatorFeeOn: FeeOn.OnlyTokenA, // optional, pass any values will initialize pool with v2 instruction, values: FeeOn.OnlyTokenA | FeeOn.OnlyTokenB | FeeOn.Both
     addSupportMintExt: true, // if your 2022 mints has verified extension
```

The upstream comment names `FeeOn.Both`. That member does not exist in `0.2.85-alpha`. The enum is `BothToken`, `OnlyTokenA`, `OnlyTokenB`.

| | Before | After |
|---|---|---|
| Parameter | No `creatorFeeOn` | `creatorFeeOn: FeeOn.OnlyTokenA` |
| Instruction | `Initialize` | `InitializeV2`, because the property is defined |
| Creator-fee path | Disabled | Enabled for the selected token |
| Creator fee accrued | None | Only if `AmmConfig.creator_fee_rate` is nonzero |

- **The parameter does not set the rate.** The rate comes from `AmmConfig.creator_fee_rate`. A zero-rate config accrues nothing.
- **Your A/B choice survives sorting.** The SDK sorts the mints into token0/token1 order. If that swaps your sides, it also swaps `OnlyTokenA` and `OnlyTokenB`, so the choice still refers to the mint you passed.
- **The owner is the creator.** The SDK passes its configured `ownerPubKey` as the creator signer. `InitializeV2` stores it in `PoolState.pool_creator`. The creator also pays the pool's rent, the create-pool fee and the initial liquidity.
- **A separate transaction fee payer is not the creator.** Setting `feePayer` does not change `pool_creator` or redirect creator fees. The `0.2.85-alpha` builders mark the creator read-only while the program requires it to be writable, so a separate `feePayer` works only if another instruction in the transaction makes the owner writable. See [Follow-ups](#follow-ups-not-fixed-here).
- **Collection.** Normal collection needs the creator's signature. Permissionless collection can be triggered by anyone, but the creator's share goes only to the creator's canonical ATAs. At collection, the configured protocol share moves to the protocol bucket first.
- **Token side.** On-chain, `OnlyToken0` and `OnlyToken1` select a token, not an input-only rule. When the selected token is the swap output, the fee comes out of the output. `BothToken` always uses the input.

The mints, amounts, start time, fee config and program IDs did not change. The demo still targets devnet program IDs, and its `execute({ sendAndConfirm: true })` call stays commented out.

### CLMM: `src/clmm/createCustomizablePool.ts`

```diff
-  const { execute } = await raydium.clmm.createCustomizablePool({
+  const { execute } = await raydium.clmm.createCustomizablePoolV2({
     programId: CLMM_PROGRAM_ID,
     // programId: DEVNET_PROGRAM_ID.CLMM_PROGRAM_ID,
     mint1,
     mint2,
     ammConfig: { ...clmmConfigs[0], id: new PublicKey(clmmConfigs[0].id), fundOwner: '', description: '' },
-    collectFeeOn: CollectFeeOn.FromInput,
+    collectFeeOnMint: new PublicKey(mint1.address), // optional, default undefined = CollectFeeOn.FromInput, values should be mint1 or mint2
     dynamicFeeConfig: dynamicFee ? new PublicKey(dynamicFee.id) : undefined, // optional
```

Two independent things changed.

- **Fee-token selection.** `collectFeeOn` is no longer accepted: `createCustomizablePool` throws "SDK no longer supports this parameter, please use collectFeeOnMint". `collectFeeOnMint` takes one of the pool's mint public keys. The SDK sorts the mints and maps it to the on-chain `Token0Only` or `Token1Only` mode. Leaving it `undefined` gives `FromInput`.
- **Pool address.** `createCustomizablePoolV2` is not a renamed canonical method. It creates an additional pool at a PDA with a nonzero `seed_index`. The SDK checks indexes 1 to 100 and uses the first free one. If all 100 are taken, it falls back to index 1 and the transaction fails, and the `forerunCreate` option skips the check and always uses index 1. `createCustomizablePool` still exists for the canonical pool and takes the same `collectFeeOnMint` and `dynamicFeeConfig` parameters.

The file still imports `CollectFeeOn`, now unused. Both demos call themselves at the bottom. The CPMM demo only simulates, because its `execute` call is commented out. The CLMM demo runs `execute({ sendAndConfirm: true })` against the mainnet CLMM program, so running it creates a live pool.

### CPMM quote warnings

In `0.2.85-alpha`, `computeSwapAmount` decides whether the creator fee is charged on input from the pool's mode alone. The program's `is_creator_fee_on_input` also uses the swap direction. The SDK also rounds the input-side trade and creator fees separately, while the program rounds their sum once. Source: `src/raydium/cpmm/cpmm.ts` and `src/raydium/cpmm/curve/calculator.ts` in `0.2.85-alpha`, and `states/pool.rs` and `curve/calculator.rs` in `raydium-cp-swap`

  - **Was:** not covered.
  - **Now:** "**CPMM creator-fee quotes in SDK `0.2.85-alpha`.** `raydium.cpmm.computeSwapAmount` can misquote pools that use the `OnlyTokenA` or `OnlyTokenB` creator-fee mode (`OnlyToken0` or `OnlyToken1` on-chain). It charges the creator fee on the same side in both swap directions, while the program switches sides by direction. Its quotes can also differ from the program by one base unit, because the SDK rounds the trade fee and the creator fee separately. ### Trade fee versus creator fee

Several overview pages described one swap fee split three or four ways, with the creator's portion taken out of the LP side. In the program, the CPMM creator fee has its own rate and its own bucket.

- **[Shared infrastructure, section 3](/docs/en/protocol-overview/shared-infrastructure#3-trade-fee-and-creator-fee-accounting):** the diagram and the mechanics. The heading was "The protocol / fund / creator fee split".

  ```text Was
                           total swap fee
                                │
                ┌───────────────┼───────────────┬──────────────┐
                ▼               ▼               ▼              ▼
          LP pool side     Protocol         Fund         Creator
          (raises k)       treasury         multisig     (LaunchLab pools)
  ```

  ```text Now
  CPMM / CLMM trade fee
    ├── LP share
    ├── Protocol share
    └── Fund share

  CPMM creator fee (independent rate, when enabled)
    └── Accrued creator bucket
        ├── Protocol share, applied at collection
        └── Remainder paid to PoolState.pool_creator
  ```

  - **Was:** "**Protocol/fund/creator portions are deducted from that LP-side accrual into per-pool counter accounts.**" and "A pool without them has a 3-way split (LP / protocol / fund). On CPMM, a fourth slot routes to the recorded pool creator."
  - **Now:** "**CPMM's creator fee uses `creator_fee_rate` independently.** It never reduces the LP, protocol, or fund shares of the trade fee. `PoolState.creator_fee_on` determines whether the creator fee is deducted from input or output on each swap. CLMM does not have this CPMM-style creator-fee bucket."
- **[Architecture, shared primitives table](/docs/en/protocol-overview/architecture):** the summary row now links to the corrected section.
  - **Was:** the row "Protocol/fund/creator fee split" read "A single trade fee is split three (sometimes four) ways at settlement. Same pattern in CPMM and CLMM, different knobs."
  - **Now:** the row "Trade and creator fees" reads "CPMM and CLMM split the trade fee between LPs, protocol, and fund. CPMM can charge a separate creator fee, with a protocol share applied when that creator bucket is collected."
- **[Constant product, CPMM convention](/docs/en/algorithms/constant-product#cpmm-convention):** the formula now matches the program. When both fees come from input, `swap_base_input` rounds their sum once and then splits it. The old formula rounded each fee separately. Source: `curve/calculator.rs`, `swap_base_input`
  - **Was:** "The trade fee is split into `trade_fee_rate` (total) and then subdivided via `protocol_fee_rate`, `fund_fee_rate`, `creator_fee_rate`."
  - **Now:** "`protocol_fee_rate` and `fund_fee_rate` subdivide the **trade fee**. `creator_fee_rate` is independent: it applies to swap volume and never reduces the trade-fee shares." and "When `creator_fee_on` selects the output token, only the trade fee is deducted from input."

  ```diff
  -trade_fee     = ceil(Δx · trade_fee_rate   / 1_000_000)
  -creator_fee   = ceil(Δx · creator_fee_rate / 1_000_000)   // its own rate on volume,
  -                                                          // NOT a slice of trade_fee
  +total_fee      = ceil(Δx · (trade_fee_rate + creator_fee_rate) / 1_000_000)
  +creator_fee    = floor(total_fee · creator_fee_rate / (trade_fee_rate + creator_fee_rate))
  +trade_fee      = total_fee − creator_fee
  ```

- **[Fee comparison](/docs/en/reference/fee-comparison):** the 84/12/4 figures are labelled as the trade-fee split, and the creator fee is listed on its own.

## Follow-ups not fixed here

- **Translations.** This pass changed English pages only. The locale copies of these pages were not updated as a set, so some may still show the `0.2.64-alpha` pin, the old `collectFeeOn` example and the old fee-split wording until they are refreshed.
- **SDK quote rounding.** The SDK's `swapBaseInput` rounds the trade fee and the input-side creator fee separately. The program rounds their sum once. Quotes can be off by one base unit. The quoting pages now warn about this; the SDK is unchanged.
- **SDK creator-fee side in quotes.** In `0.2.85-alpha`, `raydium.cpmm.computeSwapAmount` treats `OnlyTokenB` as always charged on input and `OnlyTokenA` as never, whatever the swap direction. The program charges the selected token on input or output depending on direction. On `OnlyToken0` and `OnlyToken1` pools, every token0 → token1 quote applies the creator fee to the wrong side. The pages that recommend this call ([slippage and price impact](/docs/en/algorithms/slippage-and-price-impact), the [aggregator guide](/docs/en/integration-guides/aggregator) and [Token-2022 support](/docs/en/reference/token-2022-support#transfer-fee-accounting)) now warn about it; the SDK is unchanged.
- **SDK creator account flags.** Both CPMM create builders mark the creator as read-only. The program requires it to be writable because it pays rent. This works when the owner also pays the transaction fee, as in the demos. A separate `feePayer` was not tested. The [CPMM code demos](/docs/en/products/cpmm/code-demos#create-a-cpmm-pool) and [Deploy a CPMM pool](/docs/en/quick-start/deploy-cpmm-pool) now tell readers to keep the owner as the fee payer; the SDK is unchanged.
- **Upstream demo.** The CPMM comment names `FeeOn.Both`, which does not exist, and the CLMM file still imports the unused `CollectFeeOn`.
