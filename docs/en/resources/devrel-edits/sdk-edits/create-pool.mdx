**In short.** The 16 November demo update added optional CPMM creator fees and the `createCustomizablePoolV2` CLMM builder. This review aligns the documentation with the published SDK and program behavior. It separates the CPMM creator fee from the trade fee, distinguishes the canonical and seed-indexed CLMM pool builders, and updates the SDK pin. A 26 November follow-up moves the pin to `0.2.87-alpha`, replaces obsolete CPMM quote workarounds with `computeSwapAmount`, and documents the creator-account requirement for CPMM pool creation.

## Upstream demo changes

### CPMM: `src/cpmm/createCpmmPool.ts`

The file's exported function is named `createPool`.

```diff
 import {
   CREATE_CPMM_POOL_PROGRAM,
   CREATE_CPMM_POOL_FEE_ACC,
   DEVNET_PROGRAM_ID,
   getCpmmPdaAmmConfigId,
   printSimulate,
+  FeeOn,
 } from '@raydium-io/raydium-sdk-v2'
```

```diff
     startTime: new BN(0),
     feeConfig: feeConfigs[0],
+    creatorFeeOn: FeeOn.OnlyTokenA, // optional, pass any values will initialize pool with v2 instruction, values: FeeOn.OnlyTokenA | FeeOn.OnlyTokenB | FeeOn.Both
     addSupportMintExt: true, // if your 2022 mints has verified extension
```

In the upstream comment, `FeeOn.Both` should be `FeeOn.BothToken`. The other members are `OnlyTokenA` and `OnlyTokenB`.

| | Before | After |
|---|---|---|
| Parameter | No `creatorFeeOn` | `creatorFeeOn: FeeOn.OnlyTokenA` |
| Instruction | `Initialize` | `InitializeV2`, because the property is defined |
| Creator-fee path | Disabled | Enabled for the selected token |
| Creator fee accrued | None | Only if `AmmConfig.creator_fee_rate` is nonzero |

- **The parameter does not set the rate.** The rate comes from `AmmConfig.creator_fee_rate`. A zero-rate config accrues nothing.
- **Your A/B choice survives sorting.** The SDK sorts the mints into token0/token1 order. If that swaps your sides, it also swaps `OnlyTokenA` and `OnlyTokenB`, so the choice still refers to the mint you passed.
- **The owner is the creator.** The SDK passes its configured `ownerPubKey` as the creator signer. `InitializeV2` stores it in `PoolState.pool_creator`. The creator also pays the pool's rent, the create-pool fee and the initial liquidity.
- **Account privileges.** Keep the SDK owner as the transaction fee payer. The CPMM program requires the creator to be writable, while the `0.2.87-alpha` builders mark it read-only. A separate `feePayer` works only when another instruction in the transaction marks the owner writable. Changing `feePayer` does not change `pool_creator` or redirect creator fees.
- **Collection.** Normal collection needs the creator's signature. Permissionless collection can be triggered by anyone, but the creator's share goes only to the creator's canonical ATAs. At collection, the configured protocol share moves to the protocol bucket first.
- **Token side.** On-chain, `OnlyToken0` and `OnlyToken1` select a token, not an input-only rule. When the selected token is the swap output, the fee comes out of the output. `BothToken` always uses the input.

The mints, amounts, start time, fee config and program IDs did not change. The demo continues to target devnet program IDs and simulate the transaction.

### CLMM: `src/clmm/createCustomizablePool.ts`

```diff
-  const { execute } = await raydium.clmm.createCustomizablePool({
+  const { execute } = await raydium.clmm.createCustomizablePoolV2({
     programId: CLMM_PROGRAM_ID,
     // programId: DEVNET_PROGRAM_ID.CLMM_PROGRAM_ID,
     mint1,
     mint2,
     ammConfig: { ...clmmConfigs[0], id: new PublicKey(clmmConfigs[0].id), fundOwner: '', description: '' },
-    collectFeeOn: CollectFeeOn.FromInput,
+    collectFeeOnMint: new PublicKey(mint1.address), // optional, default undefined = CollectFeeOn.FromInput, values should be mint1 or mint2
     dynamicFeeConfig: dynamicFee ? new PublicKey(dynamicFee.id) : undefined, // optional
```

Two independent things changed.

- **Fee-token selection.** `collectFeeOn` is no longer accepted: `createCustomizablePool` throws "SDK no longer supports this parameter, please use collectFeeOnMint". `collectFeeOnMint` takes one of the pool's mint public keys. The SDK sorts the mints and maps it to the on-chain `Token0Only` or `Token1Only` mode. Leaving it `undefined` gives `FromInput`.
- **Pool address.** `createCustomizablePoolV2` is not a renamed canonical method. It creates an additional pool at a PDA with a nonzero `seed_index`. The SDK checks indexes 1 to 100 and uses the first free one. If all 100 are taken, it falls back to index 1 and the transaction fails, and the `forerunCreate` option skips the check and always uses index 1 ([SDK issue #235](https://github.com/raydium-io/raydium-sdk-V2/issues/235)). `createCustomizablePool` still exists for the canonical pool and takes the same `collectFeeOnMint` and `dynamicFeeConfig` parameters.

The CLMM demo submits its transaction to the mainnet CLMM program. Confirm the cluster and program IDs before running it.

### CPMM quote warnings

**Historical correction, 2026-11-22.** The "one base unit" wording quoted below was wrong, and the warnings missed `computeSwapAmount` charging a creator fee on pools that have it off. Those corrected `0.2.85-alpha` warnings are preserved below as review history. The 26 November `0.2.87-alpha` follow-up removed them after the SDK fixed all three quote gaps; see [SDK `0.2.87-alpha` follow-up](#sdk-0287-alpha-follow-up).

In `0.2.85-alpha`, `computeSwapAmount` decides whether the creator fee is charged on input from the pool's mode alone. The program's `is_creator_fee_on_input` also uses the swap direction. The SDK also rounds the input-side trade and creator fees separately, while the program rounds their sum once. Source: `src/raydium/cpmm/cpmm.ts` and `src/raydium/cpmm/curve/calculator.ts` in `0.2.85-alpha`, and `states/pool.rs` and `curve/calculator.rs` in `raydium-cp-swap`

- **[Slippage and price impact, Sizing `minAmountOut` and `maxAmountIn`](/docs/en/algorithms/slippage-and-price-impact#sizing-minamountout-and-maxamountin):**
  - **Was:** not covered.
  - **Now:** "**CPMM creator-fee quotes in SDK `0.2.85-alpha`.** `raydium.cpmm.computeSwapAmount` can misquote pools that use the `OnlyTokenA` or `OnlyTokenB` creator-fee mode (`OnlyToken0` or `OnlyToken1` on-chain). It charges the creator fee on the same side in both swap directions, while the program switches sides by direction. Its quotes can also differ from the program by one base unit, because the SDK rounds the trade fee and the creator fee separately. For those pools, apply the rules in `products/cpmm/fees` before you set `minAmountOut`."
  - **Why:** a misquote can produce an unsafe `minAmountOut` or `maxAmountIn`; the program uses swap direction and fee enablement that this SDK helper does not model correctly.
- **[Aggregator integration, Quoting](/docs/en/integration-guides/aggregator#quoting):** the same warning, with a different last sentence.
  - **Was:** not covered.
  - **Now:** "… Read each pool's `creator_fee_on` mode and apply the rules in `products/cpmm/fees` before you rank routes through those pools."
  - **Why:** an aggregator can rank a route using the wrong output when it trusts the affected helper without applying the on-chain fee-side rules.
- **[Token-2022 support, Transfer-fee accounting](/docs/en/reference/token-2022-support#transfer-fee-accounting):** the same warning, with a different last sentence.
  - **Was:** not covered.
  - **Now:** "… For those pools, apply the rules in `products/cpmm/fees` before you show the pool fee or the received amount."

### Trade fee versus creator fee

Several overview pages described one swap fee split three or four ways, with the creator's portion taken out of the LP side. In the program, the CPMM creator fee has its own rate and its own bucket.

- **[Shared infrastructure, section 3](/docs/en/protocol-overview/shared-infrastructure#3-trade-fee-and-creator-fee-accounting):** the diagram and the mechanics. The heading was "The protocol / fund / creator fee split".

  ```text Was
                           total swap fee
                                │
                ┌───────────────┼───────────────┬──────────────┐
                ▼               ▼               ▼              ▼
          LP pool side     Protocol         Fund         Creator
          (raises k)       treasury         multisig     (LaunchLab pools)
  ```

  ```text Now
  CPMM / CLMM trade fee
    ├── LP share
    ├── Protocol share
    └── Fund share

  CPMM creator fee (independent rate, when enabled)
    └── Accrued creator bucket
        ├── Protocol share, applied at collection
        └── Remainder paid to PoolState.pool_creator
  ```

  - **Was:** "**Protocol/fund/creator portions are deducted from that LP-side accrual into per-pool counter accounts.**" and "A pool without them has a 3-way split (LP / protocol / fund). On CPMM, a fourth slot routes to the recorded pool creator."
  - **Now:** "**CPMM's creator fee uses `creator_fee_rate`.** It accrues to the creator bucket, and `PoolState.creator_fee_on` determines whether it is deducted from input or output on each swap. This bucket is specific to CPMM."
  - **Why:** the program accounts for the CPMM creator fee as an independent rate and bucket, not as a fourth share of the trade fee.
- **[Architecture, shared primitives table](/docs/en/protocol-overview/architecture):** the summary row now links to the corrected section.
  - **Was:** the row "Protocol/fund/creator fee split" read "A single trade fee is split three (sometimes four) ways at settlement. Same pattern in CPMM and CLMM, different knobs."
  - **Now:** the row "Trade and creator fees" reads "CPMM and CLMM split the trade fee between LPs, protocol, and fund. CPMM can charge a separate creator fee, with a protocol share applied when that creator bucket is collected."
  - **Why:** the old architecture summary incorrectly generalized CPMM's separate creator-fee mechanism to CLMM and folded it into the trade-fee split.
- **[Constant product, CPMM convention](/docs/en/algorithms/constant-product#cpmm-convention):** the formula now matches the program. When both fees come from input, `swap_base_input` rounds their sum once and then splits it. The old formula rounded each fee separately. Source: `curve/calculator.rs`, `swap_base_input`
  - **Was:** "The trade fee is split into `trade_fee_rate` (total) and then subdivided via `protocol_fee_rate`, `fund_fee_rate`, `creator_fee_rate`."
  - **Now:** "`protocol_fee_rate` and `fund_fee_rate` subdivide the **trade fee**. `creator_fee_rate` is a separate rate on swap volume, accounted for in its own bucket." and "When `creator_fee_on` selects the output token, only the trade fee is deducted from input."
  - **Why:** quotes and worked calculations must reproduce the program's combined rounding and separate creator-fee accounting instead of rounding two independent input fees.

  ```diff
  -trade_fee     = ceil(Δx · trade_fee_rate   / 1_000_000)
  -creator_fee   = ceil(Δx · creator_fee_rate / 1_000_000)   // its own rate on volume,
  -                                                          // NOT a slice of trade_fee
  +total_fee      = ceil(Δx · (trade_fee_rate + creator_fee_rate) / 1_000_000)
  +creator_fee    = floor(total_fee · creator_fee_rate / (trade_fee_rate + creator_fee_rate))
  +trade_fee      = total_fee − creator_fee
  ```

- **[Fee comparison](/docs/en/reference/fee-comparison):** the 84/12/4 figures are labelled as the trade-fee split, and the creator fee is listed on its own.
  - **Was:** "Fee values are percentages of the input amount, applied before pool math." The CPMM protocol row read "16% of the trade fee".
  - **Now:** "The nominal trade fee is a percentage of swap volume. Check each product's fee mode for the input/output side and any separate creator fee." The CPMM protocol row reads "12% protocol + 4% fund, both taken from the **trade fee**", and a new paragraph says "CPMM can also charge an optional creator fee at `AmmConfig.creator_fee_rate`, accounted for separately from `trade_fee_rate` and its 84/12/4 split."
  - **Why:** the old comparison merged the protocol and fund allocations and implied that every fee comes from input, which is false for a single-token CPMM creator fee on the output side.
- **[Protocol fees](/docs/en/ray/protocol-fees):** the creator fee is its own fee category with its own section.
  - **Was:** "Raydium has four user-facing fee categories." and "**Do not multiply by the wrong base.** A 12% buyback share is 12% of the swap fee, not 12% of the trade."
  - **Now:** "Raydium has five user-facing fee categories.", a new "Separate CPMM creator fee" section, and "**Do not combine CPMM fee buckets.** The creator fee has an independent rate; the protocol's share of it is applied at collection."
  - **Why:** the CPMM creator fee is a distinct user-facing charge, and its protocol share is taken from the creator bucket at collection rather than from the trade-fee split during the swap.
- **[RAY buybacks](/docs/en/ray/ray-buybacks):** the 12% applies to the CPMM and CLMM trade fee only.
  - **Was:** "12% of Raydium trading fees are used to buy back RAY."
  - **Now:** "For CPMM and CLMM, 12% of the **trade fee** is allocated to RAY buybacks." and "CPMM's optional creator fee has its own rate and is accounted for separately from these trade-fee percentages."
  - **Why:** the broad wording could be read as applying the 12% allocation to every fee stream, including the separate CPMM creator fee.
- **[Versions and migration, What CPMM gets you over AMM v4](/docs/en/protocol-overview/versions-and-migration#what-cpmm-gets-you-over-amm-v4):** the old claim about CPMM's default config was wrong.
  - **Was:** "**Better LP economics by default.** CPMM's default AmmConfig routes 100% of trade fees to LPs (with the protocol fee toggleable per-tier)."
  - **Now:** "**Configurable trade-fee tiers.** CPMM reads the LP, protocol, and fund allocation from `AmmConfig`. Its standard 0.25% config uses an 84% / 12% / 4% trade-fee split. A separate optional creator fee can apply when enabled and configured with a nonzero rate."
  - **Why:** live CPMM configuration does not route 100% of the standard tier's trade fee to LPs, so the old comparison overstated LP economics.
- **[Versions and migration, When migration is worth it](/docs/en/protocol-overview/versions-and-migration#when-migration-is-worth-it):** the old figure assumed CPMM returns the whole protocol share to LPs.
  - **Was:** "For an actively traded pool, the LP-fee uplift alone usually justifies migration within a few months."
  - **Now:** "Migration can change LP economics. Compare the live `AmmConfig` values and any separate CPMM creator fee: under CPMM's standard config, the trade fee allocates 12% to protocol and 4% to fund."
  - **Why:** the docs cannot promise a migration payoff without the pool's live fee configuration and trading conditions; the corrected text gives the inputs readers must compare.

The same pages now also describe AMM v4's 12% as an economic equivalent applied to pool growth, not an exact cut of each swap fee. That correction is recorded in [AMM v4 docs updates](/docs/en/resources/devrel-edits/amm-v4-docs-updates).

### Who receives the creator fee

- **[CPMM accounts, `PoolState`](/docs/en/products/cpmm/accounts#poolstate):** `pool_creator` is the fee recipient, not just a record of who ran a transaction.
  - **Was:** `pub pool_creator: Pubkey,             // who ran initialize`
  - **Now:** `pub pool_creator: Pubkey,             // creator-fee recipient; normally the initialize signer`, plus a new field note: "`InitializeWithPermission` records its separately supplied creator account. Paying the transaction fee does not change this field or redirect creator fees."
  - **Why:** integrators use this field to identify the creator-fee recipient, and permissioned initialization can supply an address other than the transaction fee payer.
- **[CPMM accounts, `creator_fee_on`](/docs/en/products/cpmm/accounts#poolstate):** a single-token mode is not skipped in the other direction; it takes the fee from the output instead. Source: `curve/calculator.rs`
  - **Was:** "`1` = take fee from `token_0` only (skip on `token_1 → token_0` swaps); `2` = take fee from `token_1` only."
  - **Now:** "`OnlyToken0` (`1`) always uses token0: input on `token_0 → token_1` swaps and output on `token_1 → token_0` swaps. `OnlyToken1` (`2`) does the reverse."
  - **Why:** the enum selects a token, not a direction; reversing a swap moves the selected token from input to output instead of disabling the fee.

  | `creator_fee_on` | Swap `0 → 1` | Swap `1 → 0` |
  |---|---|---|
  | `BothToken` | Input (token0) | Input (token1) |
  | `OnlyToken0` | Input (token0) | Output (token0) |
  | `OnlyToken1` | Output (token1) | Input (token1) |

- **[CPMM fees, Creator fee](/docs/en/products/cpmm/fees#creator-fee):** Burn & Earn routes LP fees, not creator fees.
  - **Was:** "Creator fees are the mechanism behind Raydium's \"Burn & Earn\" pattern: LP tokens are locked under the [LP Lock](/docs/en/reference/program-addresses) program so the creator cannot withdraw liquidity, but the accrued creator fees can still be collected indefinitely."
  - **Now:** "Burn & Earn locks an LP position under the [LP Lock](/docs/en/reference/program-addresses) program and routes that position's LP fees to the Fee Key holder. The CPMM creator fee stays with `PoolState.pool_creator`, less the protocol share at collection, whoever holds the locked LP or the Fee Key."
  - **Why:** LP Lock and the CPMM program track different recipients; transferring a Fee Key does not transfer `PoolState.pool_creator`.
- **[Burn & Earn](/docs/en/user-flows/burn-and-earn):** the Fee Key holder receives the locked position's LP fees only.
  - **Was:** "Whoever holds it at the time of a `collectFees` call receives the fees."
  - **Now:** "Whoever holds it at the time of a `collectFees` call receives the locked position's LP fees." and "Locking an LP position or transferring its Fee Key does not transfer the `pool_creator` designation or its creator-fee stream."
  - **Why:** the unqualified word "fees" blurred LP-position revenue with the separate creator-fee bucket and could misstate what a Fee Key transfer conveys.
- **[FAQ](/docs/en/getting-started/faq#who-receives-cpmm-creator-fees):** the Burn & Earn answer is narrowed, and a new question covers CPMM creator fees. The LaunchLab answers are unchanged.
  - **Was:** "…retaining a **Fee Key NFT** that continues to collect trading fees."
  - **Now:** "…retaining a **Fee Key NFT** that continues to collect that position's LP trading fees." and a new entry, "Who receives CPMM creator fees?"
  - **Why:** readers need separate answers for Fee Key LP fees and the creator fees paid to the address stored in the CPMM pool state.
- **[CPMM chapter landing, Instructions card](/docs/en/products/cpmm#chapter-contents):** the card now lists `InitializeV2` and creator-fee collection.
  - **Was:** "Initialize, Deposit, Withdraw, SwapBaseInput, SwapBaseOutput, CollectFundFee, CollectProtocolFee, UpdatePoolStatus."
  - **Now:** "Initialize and InitializeV2, deposits, withdrawals, swaps, creator-fee collection, protocol and fund collection, and pool status."
  - **Why:** the chapter summary must expose the deployed V2 initialization and creator-fee collection paths documented inside the chapter.

### SDK `0.2.87-alpha` follow-up

The published `0.2.87-alpha` package resolves the three CPMM creator-fee quote gaps found in `0.2.85-alpha`. `computeSwapAmount` now checks `enableCreatorFee`, derives the fee side from both the configured mode and swap direction, and uses the program's combined trade-plus-creator-fee rounding before it splits the two fees.

- **Canonical pin and translations:**
  - **Was:** English code-demo surfaces targeted `0.2.85-alpha`, while 11 current pin surfaces in each locale still targeted `0.2.64-alpha`.
  - **Now:** current English and localized SDK-version surfaces target `0.2.87-alpha`. Historical changelog entries and version comparisons keep the versions they describe.
  - **Why:** one canonical pin prevents readers from combining examples and types from different prerelease packages.
- **CPMM quote examples and warnings:**
  - **Was:** the CPMM code demos and CLI script bypassed `computeSwapAmount` with manual `CurveCalculator` logic. The slippage, aggregator, Token-2022, and deploy-pool pages warned about the three SDK defects.
  - **Now:** the CPMM base-input and base-output demos and the CLI script call `raydium.cpmm.computeSwapAmount`. The affected pages remove the obsolete warnings and describe the fixed behavior.
  - **Why:** keeping a manual workaround after the helper is fixed would duplicate fee logic and could drift from later program changes.
- **CPMM create-pool fee payer:**
  - **Was:** the docs said a separate `feePayer` was unverified and might fail.
  - **Now:** the docs state that it fails unless another instruction promotes the SDK owner to writable. The create builders still mark `creator` read-only, while both program initializers require `#[account(mut)] creator`.
  - **Why:** the compiled transaction must grant the creator the writable privilege required by both program initializers.
