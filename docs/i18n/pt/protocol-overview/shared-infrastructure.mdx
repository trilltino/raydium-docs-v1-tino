## O que "compartilhado" significa aqui

Três tipos de compartilhamento percorrem a base de código:

- **Convenções compartilhadas.** Os programas reutilizam padrões de derivação de PDA, contas de configuração, contabilidade de taxas e contas de observação, mas cada programa define suas próprias seeds e seu comportamento. Nomes de campos parecidos não garantem regras de liquidação idênticas.
- **Compartilhamento de conta.** Um punhado de contas são *literalmente* o mesmo registro em muitos pools (o PDA de autoridade global em CPMM, as contas AmmConfig).
- **Compartilhamento off-chain.** Uma API REST e um SDK TypeScript fronteiam todos os quatro programas. Os integradores interagem com um host HTTP e um pacote NPM independentemente de qual programa acabam chamando.

Os cinco primitivos abaixo cobrem tudo que cruza limites de programa.

## 1. PDAs de autoridade

Todo programa Raydium tem exatamente um PDA que possui seus cofres de token. Os usuários nunca mantêm autoridade de cofre diretamente — o PDA de autoridade é o único signatário que pode mover fundos para fora, e só assina quando uma instrução de programa válida o diz.

O padrão é idêntico entre produtos; as sementes diferem:

| Programa | Sementes do PDA de autoridade | Notas |
|---------|---------------------|-------|
| **AMM v4** | `[b"amm authority"]` | **PDA único compartilhado por todos os pools AMM v4.** Seu bump é espelhado em cada `AmmInfo` como `nonce`. |
| **CPMM** | `[b"vault_and_lp_mint_auth_seed"]` | **PDA único compartilhado por todos os pools CPMM.** Sem semente específica de pool. |
| **CLMM** | *(nenhum — o próprio `pool_state` é a autoridade do cofre)* | Por pool. Os cofres são PDAs em `[b"pool_vault", pool_state, mint]`, de propriedade de e assinados por `pool_state`. O CLMM não tem PDA global de autoridade de cofre. |
| **Farm v3 / v5 / v6** | `[farmId]` | Por farm. O PDA possui cofres de staking + recompensas para esse farm. |
| **LaunchLab** | `[b"vault_auth_seed"]` | **PDA único compartilhado por todos os lançamentos.** Dois outros PDAs globais, `[b"platform_fee_vault_auth_seed"]` e `[b"creator_fee_vault_auth_seed"]`, possuem os cofres de taxa agregados. |

Algumas coisas decorrem disso:

- Para AMM v4, CPMM e LaunchLab, o PDA de autoridade é **uma conta global** — cada pool ou lançamento desse tipo a usa. Se você está fazendo CPI em CPMM, você precisa dela uma vez, não por pool.
- O CLMM é a exceção: não existe nenhum PDA de autoridade. Cada cofre é um PDA semeado no pool e no mint, e a conta do pool assina por ele.
- Para autoridades por farm, você deriva o PDA do ID do farm. O SDK faz isso em `getPoolKeys` / `getFarmKeys`; se você está integrando diretamente, você deriva com `findProgramAddressSync`.
- **A propriedade do cofre não pode ser alterada.** Uma vez que uma conta de token é criada com o PDA de autoridade como proprietário, apenas esse PDA — invocado pelo programa — pode transferir para fora. Não há substituição de administrador.

Para as sementes exatas e layouts de ATA por programa, veja [`products/cpmm/accounts`](/docs/i18n/pt/products/cpmm/accounts), [`products/clmm/accounts`](/docs/i18n/pt/products/clmm/accounts), [`products/amm-v4/accounts`](/docs/i18n/pt/products/amm-v4/accounts), [`products/farm-staking/accounts`](/docs/i18n/pt/products/farm-staking/accounts), [`products/launchlab/accounts`](/docs/i18n/pt/products/launchlab/accounts).

## 2. Contas de administrador e configuração

CPMM e CLMM compartilham um padrão de conta de configuração chamado **`AmmConfig`**: uma pequena conta global, indexada por um `u16`, mantendo as taxas de taxa e destinos de administrador que se aplicam a um *nível de taxa* inteiro. Os pools se vinculam a uma configuração na criação e nunca se re-vinculam.

```rust
// CPMM AmmConfig (abreviado — a versão CLMM é estruturalmente similar)
pub struct AmmConfig {
    pub bump: u8,
    pub disable_create_pool: bool,        // gate new pool creation in this tier
    pub index: u16,                       // tier index
    pub trade_fee_rate: u64,              // fraction of trade going to fees
    pub protocol_fee_rate: u64,           // fraction of trade fee to protocol
    pub fund_fee_rate: u64,               // fraction of trade fee to fund
    pub create_pool_fee: u64,             // one-time per-pool creation fee
    pub protocol_owner: Pubkey,           // signer for CollectProtocolFee
    pub fund_owner: Pubkey,               // signer for CollectFundFee
    pub padding: [u64; 16],
}
```

**Regras da estrada:**

- **Os níveis de taxa são globais.** Quando um pool diz "este é um pool de 0,25%", significa que se vincula ao AmmConfig cuja `trade_fee_rate` era 0,25% no momento da criação. Não há substituição de taxa por pool.
- **Uma configuração pode ser alterada, mas os pools não a seguem.** Se a autoridade de configuração editar um AmmConfig, cada pool existente vinculado a essa configuração pega a nova taxa imediatamente. Isso é um recurso, não um bug; é assim que as mudanças econômicas no nível do protocolo se propagam sem migrações por pool.
- **`disable_create_pool` é a alavanca de descontinuação.** Quando um nível de taxa é descontinuado, o multisig do protocolo define esse sinalizador — os pools existentes continuam funcionando, mas nenhum novo pool pode escolher o nível.
- **`protocol_owner` / `fund_owner`** são os *signatários* para chamadas de coleta de taxas. Defini-los como um multisig é o que controla a retirada de taxas. Eles NÃO são os endereços de destino das taxas em si; isso é `protocol_fee_destination` / `fund_fee_destination` na mesma conta.

AMM v4 não tem `AmmConfig` — seus parâmetros de taxa são por pool, codificados na criação. Farm e LaunchLab têm seus próprios equivalentes (`FarmConfig`, `LaunchConfig`) cobertos em seus respectivos capítulos.

Uma tabela completa de quem pode alterar o quê está em [`security/admin-and-multisig`](/docs/i18n/pt/security/admin-and-multisig). As divisões de taxas atuais voltadas para o usuário estão em [`ray/protocol-fees`](/docs/i18n/pt/ray/protocol-fees).

## 3. Contabilidade da taxa de negociação e da taxa do criador

O CPMM e o CLMM dividem a **taxa de negociação** entre LPs, protocolo e fundo. O CPMM também pode cobrar uma taxa opcional do criador com uma alíquota própria. Não modele essa taxa do criador como uma quarta fatia da taxa de negociação:

```
CPMM / CLMM trade fee
  ├── LP share
  ├── Protocol share
  └── Fund share

CPMM creator fee (independent rate, when enabled)
  └── Accrued creator bucket
      ├── Protocol share, applied at collection
      └── Remainder paid to PoolState.pool_creator
```

Mecanicamente:

1. **A taxa de negociação usa `trade_fee_rate`.** A parte dos LPs permanece na contabilidade do pool. O CPMM cobra sua taxa de negociação da entrada do swap. O CLMM também suporta cobrança de taxa em um só lado no nível do pool, então verifique o modo de taxa do produto antes de supor uma dedução apenas na entrada.
2. **A taxa do criador do CPMM usa `creator_fee_rate` de forma independente.** Ela nunca reduz as partes dos LPs, do protocolo ou do fundo na taxa de negociação. `PoolState.creator_fee_on` determina se a taxa do criador é deduzida da entrada ou da saída em cada swap. O CLMM não tem esse bucket de taxa do criador no estilo do CPMM.
3. **As partes que não são de LP se acumulam em contadores separados.** Elas permanecem nos vaults, mas ficam fora das reservas usadas pela curva até que a instrução de coleta correspondente seja executada.
4. **A coleta define os destinos.** Os caminhos do protocolo e do fundo exigem a respectiva autoridade de `AmmConfig`. A coleta do criador no CPMM exige a assinatura do criador registrado ou usa o caminho sem permissão, que qualquer pagador pode acionar, mas que fixa como destino as ATAs canônicas desse criador. Os dois caminhos do criador aplicam, na coleta, a parte configurada do protocolo sobre o bucket do criador.

Algumas observações que carregam carga:

- **Os percentuais de divisão se aplicam à taxa de negociação, não à negociação inteira.** Uma taxa de negociação de 0,25% com uma parte de 12% para o protocolo dá ao protocolo `0.25% × 12% = 0.03%` da negociação, antes de considerar qualquer taxa do criador separada.
- **As taxas do criador do CPMM são opcionais por pool e fixadas na criação.** As graduações do LaunchLab podem ativá-las por meio de `InitializeWithPermission`. Desde 2026-10-30, qualquer criador pode ativar o caminho por meio de `InitializeV2`; o SDK escolhe essa instrução quando `creatorFeeOn` é definido. Ainda é preciso um `creator_fee_rate` diferente de zero para que algo se acumule.
- **O AMM v4 usa liquidação diferida de PnL.** Sua fração `pnl_numerator / pnl_denominator` se aplica ao crescimento calculado por `calc_take_pnl`, não diretamente à taxa de cada swap. Ele não tem bucket de fundo nem de criador.
- **Fundo vs. protocolo** — ambos são destinos da tesouraria do protocolo, mas têm signatários e usos previstos diferentes. `protocol` historicamente financia as operações; `fund` é a tesouraria de longo prazo.

As taxas específicas estão em [`reference/fee-comparison`](/docs/i18n/pt/reference/fee-comparison) e [`ray/protocol-fees`](/docs/i18n/pt/ray/protocol-fees).

## 4. Contas de observação (buffer de anel TWAP)

Tanto CPMM quanto CLMM mantêm uma **conta de observação** por pool — um buffer de anel de tamanho fixo de amostras `(timestamp, cumulative_price)` que outros contratos podem usar para derivar um TWAP resistente a manipulação.

```rust
// CPMM ObservationState (abreviado)
pub struct ObservationState {
    pub initialized: bool,
    pub observation_index: u16,            // next slot to overwrite
    pub pool_id: Pubkey,
    pub observations: [Observation; OBSERVATION_NUM],
    pub padding: [u64; 4],
}

pub struct Observation {
    pub block_timestamp: u64,
    pub cumulative_token_0_price_x32: u128,  // sum of (price × dt) since init
    pub cumulative_token_1_price_x32: u128,
}
```

Como funciona:

- **Cada swap chama `update_observation`.** O programa lê o preço atual, multiplica pelos segundos decorridos desde a observação anterior e o adiciona ao contador cumulativo. A nova entrada sobrescreve o slot mais antigo (estilo buffer de anel).
- **TWAP sobre uma janela** = `(cumul[end] − cumul[start]) / (timestamp[end] − timestamp[start])`. Os consumidores escolhem duas observações entre a janela desejada e dividem.
- **O próprio Raydium não usa o TWAP para precificação.** A matemática AMM lê as reservas de spot diretamente. As observações são uma externalidade — Raydium paga o custo de escrevê-las para que outros contratos possam ler.
- **AMM v4 não tem conta de observação.** É mais antigo que o design ObservationState; os integradores que desejam um TWAP v4 têm que computar um off-chain do histórico de logs.

Detalhes de layout e matemática de indexação estão em [`products/cpmm/accounts`](/docs/i18n/pt/products/cpmm/accounts) e [`products/clmm/accounts`](/docs/i18n/pt/products/clmm/accounts).

## 5. API REST + SDK + IDL

A superfície off-chain é um único trio usado por cada produto:

- **API REST** — `https://api-v3.raydium.io`. Uma visão indexada principalmente de leitura de todo o estado on-chain mais um mecanismo de cotação. Um host, um esquema.
- **SDK TypeScript** — `@raydium-io/raydium-sdk-v2` no NPM. Constrói e assina transações para cada programa. Fala com a API para cotações/metadados, fala com um RPC Solana para atualizações de estado pré-assinatura.
- **Registro IDL** — IDLs Anchor para cada programa publicado vivem no repositório [`raydium-idl`](https://github.com/raydium-io/raydium-idl) (um JSON por programa: CPMM, CLMM, LaunchLab). O SDK TypeScript consome esses IDLs internamente; clientes Rust / Python downstream regeneram dos mesmos arquivos.

O limite entre eles é nítido:

| Peça | Lê de | Escreve para | Tolerância de desatualização |
|-------|-----------|-----------|-----------------|
| API REST | Indexador (analisa logs da cadeia) | — (somente leitura para integradores) | Alguns segundos |
| SDK | API + RPC | Constrói transações; não transmite | Nenhuma — deve re-buscar estado pré-assinatura |
| IDL | Fonte do programa | — | Versionado por atualização de programa |

Um erro comum é alimentar a saída da API REST diretamente em uma transação. Não faça isso — re-busque o estado relevante do pool/posição de um RPC Solana no slot que você está assinando. O SDK faz isso automaticamente para fluxos de primeira parte; se você contornar o SDK, você tem que fazer isso você mesmo.

A referência completa está em [`sdk-api/`](/docs/i18n/pt/sdk-api), com a superfície IDL especificamente em [`sdk-api/anchor-idl`](/docs/i18n/pt/sdk-api/anchor-idl).

## 6. Indexadores e feeds de preço

A API REST é alimentada pelo próprio indexador do Raydium, que se inscreve em logs de programa de uma frota de RPCs Solana e escreve registros desnormalizados em um armazenamento SQL. Duas consequências para integradores:

- **O indexador é a única coisa que "sabe sobre" estado entre programas.** Mapear um pool CPMM para seu equivalente CLMM, computar um número de volume de 24h entre versões de programa, pegar um farm associado a um mint LP — tudo isso é trabalho de indexador. Os próprios programas não fazem isso.
- **O tempo de inatividade do indexador é o tempo de inatividade da API.** Se a API retorna dados desatualizados ou vazios, o indexador é o suspeito. O estado on-chain não é afetado; integradores com seu próprio RPC e SDK podem continuar transacionando.

Os feeds de preço são uma preocupação separada. A API publica um campo `priceUsd` na maioria das respostas de pool; isso é computado off-chain a partir de um snapshot da visão do indexador das reservas do pool e um preço de referência citado (pools USDC como o pivô comum). É bom o suficiente para UI; não é seguro usar como um oráculo on-chain. Use o TWAP de observação para isso.

## O que não é compartilhado

Vale a pena listar explicitamente, porque novos leitores frequentemente assumem mais compartilhamento do que existe:

- **Os programas não chamam uns aos outros.** Um swap CPMM nunca faz CPI em CLMM ou AMM v4. O único programa que compõe múltiplos AMMs é o programa AMM Routing — e esse é em si fino, apenas emitindo CPIs em cada AMM em sequência.
- **Nenhuma autoridade de atualização compartilhada entre programas.** Cada programa on-chain tem sua própria chave de atualização de programa (um multisig 3/4 mais um timelock de 24h). Elas não estão vinculadas.
- **Nenhum estado compartilhado entre farms e AMMs.** Um farm não sabe qual LP que ele estaca é de um pool CPMM, um mint NFT de posição CLMM ou um token SPL não relacionado. O programa farm trata o mint de staking como opaco.
- **Nenhuma dependência de oráculo.** A precificação é reservas on-chain. Não há fallback Pyth/Switchboard; o AMM não verifica um oráculo antes de limpar.
